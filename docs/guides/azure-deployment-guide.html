1What to provision

The app is a single Node 20 container (multi‑stage Dockerfile, Next.js standalone output, listens on port 3000 as a non‑root user) plus one PostgreSQL database. That's the whole footprint.

ResourceNeeded?Notes
App host Required Azure App Service (Web App for Containers) or Azure Container Apps Runs the repo's own Dockerfile (node:20-alpine, EXPOSE 3000, CMD ["node","server.js"]). Scale to exactly 1 instance — rate limiting, query cancellation, and schema‑introspection status are all in‑process state (see Gotchas).
App database Required Azure Database for PostgreSQL — Flexible Server Required in auth mode (APP_DATABASE_URL). Stores users, connections (AES‑256‑GCM‑encrypted credentials), schemas, reports, query log. Smallest burstable tier (B1ms) is fine to start. 2Microsoft Entra ID setup

  1. Create the app registration

    Entra admin center → App registrations → New registration. Add a Web redirect URI:

    https://<your-host>/api/auth/callback/authentik

    That path is not a typo — the app's OIDC provider id defaults to authentik, and Auth.js builds the callback path from it. If you'd rather see /api/auth/callback/entra, set AUTH_OIDC_PROVIDER_ID=entra in the env and register that URI instead. Changing the provider id later invalidates the registered redirect URI, so pick once.

  2. Create a client secret

    Certificates & secrets → New client secret. Copy the value (not the secret ID) into AUTH_OIDC_CLIENT_SECRET. Note the expiry (the portal caps it at 24 months; tenant policy may force shorter) and put a rotation reminder on the calendar — expiry silently breaks all sign‑ins.

  3. Decide how admins are identified — App Role recommended

    AUTH_ADMIN_GROUP is matched case‑insensitively against the merged groups + roles token claims. Two options:

    • App Role (recommended): App registration → App roles → create a role with value DataQuery.Admin. Assign users/groups under Enterprise applications → Users and groups. Set AUTH_ADMIN_GROUP=DataQuery.Admin. Roles arrive in the roles claim automatically and are never subject to the groups‑overage limit.
    • Security group: App registration → Token configuration → Add groups claim → Security groups (make sure the ID token box is checked). Entra emits group object GUIDs, not names, so set AUTH_ADMIN_GROUP=<group-object-id-guid>.

  4. Restrict who can sign in (optional)

    By default anyone in the tenant who can authenticate may use the app. Two complementary controls:

    • App‑side — AUTH_ALLOWED_GROUPS: comma‑separated group names, group object GUIDs, or App Role values, matched exactly like AUTH_ADMIN_GROUP. When set, users holding none of the listed identities are denied at sign‑in (they land on /auth/error with an "Access denied" message), and already‑signed‑in sessions are cut off on their next request. Empty/unset = everyone allowed. Use an App Role value here (e.g. create a second role DataQuery.User) — a user hitting the groups‑overage limit has no groups claim and the gate fails closed, but the roles claim is never subject to overage.
    • IdP‑side — "Assignment required?": Enterprise applications → your app → Properties → set Assignment required? to Yes, then assign users/groups under Users and groups. Entra then refuses to issue tokens to unassigned users before the app is ever involved. Strongest control; combining both is good defense in depth.

  5. Verify the token

    After first sign‑in, decode the ID token (Entra sign‑in logs, or jwt.ms) and confirm: an email is present (email, falling back to preferred_username, then upn); your roles or groups claim is present; and _claim_names/_claim_sources do not appear in place of groups (that's the overage indicator — see Gotchas).

Scopes are mandatory to override. The app's default scope string is openid email profile groups — Authentik's shape. Entra has no groups scope and will reject the authorization request. You must set AUTH_OIDC_SCOPES=openid email profile.

3Sample .env for Entra

Every variable below is read by the app (verified against the code). Generate the two random keys with openssl rand -hex 32.

# ── OpenAI (always required) ─────────────────────────────────────────
OPENAI_API_KEY=sk-...
OPENAI_MODEL=gpt-5.6-sol            # must be set: generate/enhance/revise have NO fallback;
                                    # the other AI routes silently fall back to a hardcoded gpt-5.6-terra
OPENAI_REASONING_EFFORT=            # optional: none|minimal|low|medium|high|xhigh|max (gpt-5/o-series)

# ── Auth: Microsoft Entra ID (all three OIDC_* enable auth mode) ─────
AUTH_OIDC_ISSUER=https://login.microsoftonline.com/<tenant-id>/v2.0
AUTH_OIDC_CLIENT_ID=<application-client-id>
AUTH_OIDC_CLIENT_SECRET=<client-secret-value>
AUTH_OIDC_PROVIDER_NAME=Microsoft   # sign-in button label
AUTH_OIDC_SCOPES=openid email profile   # REQUIRED for Entra (no "groups" scope)
# AUTH_OIDC_PROVIDER_ID=entra       # optional; default "authentik" — callback path must match

AUTH_SECRET=<openssl rand -hex 32>
AUTH_URL=https://dataquery.example.com   # public HTTPS origin; also drives secure cookies
NEXTAUTH_URL=https://dataquery.example.com   # legacy alias next-auth/jwt still reads
# AUTH_TRUST_HOST is NOT needed — the app hardcodes trustHost: true in code
AUTH_ADMIN_GROUP=DataQuery.Admin    # App Role value, or a group object GUID; comma-separated OK
AUTH_ALLOWED_GROUPS=                # optional sign-in gate; empty = everyone. Prefer an App Role
                                    # value (e.g. DataQuery.User) — overage users fail closed on groups

# ── App database (required when auth is enabled) ─────────────────────
# Azure PG enforces TLS and the pool sets no ssl option — put sslmode in the URL.
# sslmode=require works but skips cert verification; Microsoft recommends verify-full (see §4)
APP_DATABASE_URL=postgres://dqadmin:<password>@<server>.postgres.database.azure.com:5432/dataquery_app?sslmode=require
APP_ENCRYPTION_KEY=<openssl rand -hex 32>   # exactly 64 hex chars; encrypts stored DB credentials

# ── Leave unset in production ─────────────────────────────────────────
DEMO_RATE_LIMIT=                    # demo-only IP rate limit
TRUSTED_PROXIES=                    # only if you front the app with your own reverse proxy
EVAL_ALLOW_MODEL_OVERRIDE=          # eval harness only — never in production
Never rotate APP_ENCRYPTION_KEY casually. It decrypts every stored database credential. Changing it orphans all saved connection passwords — there is no re‑encryption tool. Back it up in Key Vault from day one.

4Azure‑side settings

App Service / Container Apps

  • WEBSITES_PORT=3000 (App Service) or target port 3000 (Container Apps) — the container listens on 3000, HOSTNAME=0.0.0.0.
  • Always On: enabled, and max 1 instance / no autoscale-out.
  • Store secrets as Key Vault references (@Microsoft.KeyVault(SecretUri=...)) with a system‑assigned managed identity granted Key Vault Secrets User.
  • Set AUTH_URL to the final public hostname (custom domain if you bind one) before first sign‑in — it must match the redirect URI's host registered in Entra.
  • Health check path: /api/config/auth-status is a cheap unauthenticated endpoint — but it is liveness only: it never touches the database, so it stays green even if migrations failed or Postgres is unreachable (exactly the failure mode in step 7). With a single instance the health check can't rotate the instance out anyway; note that enabling or changing the health check path restarts the app.
  • TLS: App Service terminates HTTPS for you; no extra proxy config or TRUSTED_PROXIES needed unless you add your own front door/proxy and use DEMO_RATE_LIMIT (which you shouldn't in production).

Key Vault wiring

No code changes are needed: the codebase has no NEXT_PUBLIC_* (build‑time) variables — every setting is read server‑side at runtime via process.env, and Key Vault references resolve into ordinary environment variables before the container starts. The setup is entirely Azure‑side:

  1. Enable the managed identity

    Web App → Identity → System assigned → On.

  2. Grant it access to the vault

    RBAC vault (the default): assign the identity the Key Vault Secrets User role scoped to the vault. Legacy access-policy vault: grant Get on secrets.

  3. Write app settings as references

    AUTH_OIDC_CLIENT_SECRET = @Microsoft.KeyVault(SecretUri=https://dataquery-kv.vault.azure.net/secrets/entra-client-secret)

    Use a versionless SecretUri (no version segment) so the reference always resolves the latest version of the secret. Do the same for OPENAI_API_KEY, AUTH_SECRET, APP_ENCRYPTION_KEY, and APP_DATABASE_URL — store the whole connection string as one secret; special characters in the password are fine since the app settings layer never parses it.

  4. Plan for the vault firewall — the "trusted services" checkbox does NOT work here

    If the vault restricts network access, Key Vault references from App Service are not covered by "Allow trusted Microsoft services to bypass this firewall" (App Service is only on the trusted list for certificate deployment). Microsoft also discourages allowlisting the app's outbound IPs, since secret requests may not originate from them. The reliable pattern is regional VNet integration on the Web App plus a vault network rule for that subnet (on Linux, also set vnetRouteAllEnabled=true). Simplest working setup: leave the vault on public network access and rely on RBAC + the managed identity for access control.

A broken reference passes the literal string through. When a reference fails to resolve, the env var arrives containing the literal @Microsoft.KeyVault(...) text — never empty. Since the AUTH_OIDC_* vars are then non‑empty, auth mode still activates, just with garbage values: the symptoms are OIDC sign‑in failures and app‑DB connection errors from a literal‑string APP_DATABASE_URL. After deploying, check the app settings blade — each reference shows a green check or red X — and confirm "Sign in with Microsoft" actually completes a login.

Rotation isn't instant: App Service re-resolves versionless references periodically (roughly daily) or on restart. When you rotate the Entra client secret, restart the app to pick it up immediately.

Container Apps instead of App Service: the mechanism differs slightly — define secrets on the Container App with a Key Vault URI + managed identity, then map them to env vars. Same outcome, still no code change.

PostgreSQL Flexible Server

  • Create the database itself: CREATE DATABASE dataquery_app; — migrations create the tables, not the database.
  • Networking: either firewall rules allowing the app's outbound IPs (bootstrap option: "Allow public access from any Azure service" — but note that allows connections from any Azure customer's subscription, so tighten to the App Service outbound IP list promptly), or — better — VNet integration on the app plus a private endpoint on the server.
  • TLS is enforced by default (require_secure_transport=on); the app's pool passes no SSL options, so the sslmode suffix on APP_DATABASE_URL is what makes the connection work. ?sslmode=require connects without any CA setup but skips certificate verification; Microsoft's recommendation for production is verify-full with the Microsoft RSA / DigiCert Global root CAs in the trust store.
  • Backups are automatic and can't be disabled — 7‑day retention by default, configurable up to 35. This DB holds every user's saved connections and reports, so consider raising it.

Network egress

  • Allow outbound HTTPS to api.openai.com and login.microsoftonline.com. If you lock egress down with a firewall/NSG, these two plus the app DB are the minimum.
  • Each target database your team queries (the whole point of the tool) also needs a network path from the app — firewall allowances or VNet peering per database server.

Entra hygiene

  • Client secret expiry: calendar the rotation; consider a 6‑month expiry with a standing reminder.
  • If you require admin consent for apps in your tenant, grant it for the delegated openid email profile permissions (Microsoft Graph → User.Read equivalent basic sign-in).
  • Optionally restrict sign‑in to assigned users only: Enterprise application → Properties → "Assignment required = Yes", then assign your team. Pairs well with the app‑side AUTH_ALLOWED_GROUPS gate (section 2, step 4).

5Getting the service running

  1. Pick the public hostname first

    Decide the Web App name now (it fixes your hostname: https://<name>.azurewebsites.net) — the Entra redirect URI in step 3 and AUTH_URL both depend on it. If you plan to use a custom domain instead, know that it needs domain verification (TXT/CNAME) and a certificate binding (App Service Managed Certificate is free) before it can serve the OIDC callback — bind it before first sign‑in, or start on the azurewebsites.net hostname and update AUTH_URL + the Entra redirect URI together when you switch.

  2. Provision PostgreSQL and create the database

    az postgres flexible-server create -g dataquery-rg -n dataquery-pg \
  --tier Burstable --sku-name Standard_B1ms --version 16 \
  --admin-user dqadmin --admin-password '<strong-password>'
az postgres flexible-server db create -g dataquery-rg -s dataquery-pg -n dataquery_app

    Any recent major version works (the repo's own compose stack runs PG 15); pick 16/17 for a longer support runway.

  3. Register the app in Entra

    Follow section 2: registration + Web redirect URI (using the hostname from step 1), client secret, App Role DataQuery.Admin, and (only if using groups instead) the groups claim in Token configuration.

  4. Create the Key Vault, generate secrets, and load it

    az keyvault create -g dataquery-rg -n dataquery-kv --enable-rbac-authorization
openssl rand -hex 32   # → AUTH_SECRET
openssl rand -hex 32   # → APP_ENCRYPTION_KEY

    Store both, plus OPENAI_API_KEY, the Entra client secret, and the full APP_DATABASE_URL, as vault secrets. The Web App's managed identity can only be wired up after the Web App exists — that happens in step 6 (see section 4's Key Vault wiring for the details).

  5. Build and push the image

    az acr create -g dataquery-rg -n dataqueryacr --sku Basic
az acr build -r dataqueryacr -t dataquery-pro:1.0 .   # uses the repo's Dockerfile

    The Dockerfile is multi‑stage (pnpm install → pnpm run build → standalone runner); no local Docker daemon needed with az acr build.

  6. Create the Web App and give it pull access to ACR

    az appservice plan create -g dataquery-rg -n dataquery-plan --sku B1 --is-linux
az webapp create -g dataquery-rg -p dataquery-plan -n dataquery-pro \
  --container-image-name dataqueryacr.azurecr.io/dataquery-pro:1.0

    The image pull will fail until you authenticate it — a Basic ACR has the admin user disabled by default and az webapp create configures no registry credentials. Preferred fix (managed identity):

    az webapp identity assign -g dataquery-rg -n dataquery-pro   # note the principalId it prints
az role assignment create --assignee <principalId> --role AcrPull \
  --scope $(az acr show -n dataqueryacr --query id -o tsv)
az webapp config set -g dataquery-rg -n dataquery-pro \
  --generic-configurations '{"acrUseManagedIdentityCreds": true}'

    Quick-and-dirty alternative: az acr update -n dataqueryacr --admin-enabled true and pass --container-registry-user/--container-registry-password instead. The identity assigned here is the same one section 4's Key Vault wiring needs — grant it Key Vault Secrets User on the vault now too.

  7. Set the app settings

    Every variable from section 3, with Key Vault references for the secrets, plus WEBSITES_PORT=3000:

    az webapp config appsettings set -g dataquery-rg -n dataquery-pro --settings \
  WEBSITES_PORT=3000 \
  AUTH_URL=https://dataquery-pro.azurewebsites.net \
  NEXTAUTH_URL=https://dataquery-pro.azurewebsites.net \
  AUTH_OIDC_ISSUER=https://login.microsoftonline.com/<tenant-id>/v2.0 \
  AUTH_OIDC_CLIENT_ID=<application-client-id> \
  "AUTH_OIDC_SCOPES=openid email profile" \
  AUTH_OIDC_PROVIDER_NAME=Microsoft \
  AUTH_ADMIN_GROUP=DataQuery.Admin \
  AUTH_ALLOWED_GROUPS=DataQuery.User \
  OPENAI_MODEL=gpt-5.6-sol \
  "AUTH_OIDC_CLIENT_SECRET=@Microsoft.KeyVault(SecretUri=https://dataquery-kv.vault.azure.net/secrets/entra-client-secret)" \
  "AUTH_SECRET=@Microsoft.KeyVault(SecretUri=https://dataquery-kv.vault.azure.net/secrets/auth-secret)" \
  "APP_ENCRYPTION_KEY=@Microsoft.KeyVault(SecretUri=https://dataquery-kv.vault.azure.net/secrets/app-encryption-key)" \
  "APP_DATABASE_URL=@Microsoft.KeyVault(SecretUri=https://dataquery-kv.vault.azure.net/secrets/app-database-url)" \
  "OPENAI_API_KEY=@Microsoft.KeyVault(SecretUri=https://dataquery-kv.vault.azure.net/secrets/openai-api-key)"

  8. Open the database firewall to the app

    Add the Web App's outbound IPs to the Flexible Server firewall (or wire up VNet integration + private endpoint). Note the container has been running since step 6 and failing to reach the database — expect [instrumentation] Migration failed: in the logs until the restart in the next step. That's expected, not a broken deployment.

  9. Start it and verify migrations

    Restart the app and check the log stream for:

    [instrumentation] Database migrations complete

    All migrations in lib/db/migrations/ (001–007 at the time of writing) run automatically on startup. Watch for this line specifically — a migration failure is logged ([instrumentation] Migration failed:) but does not crash the container, so the app can look healthy while the schema is missing.

  10. Sign in and confirm admin

    Visit the site, sign in with a user assigned the DataQuery.Admin App Role, and confirm the Admin link appears in the user menu. Add your first database connection under Admin → server connections (or per‑user under Database), upload the schema to OpenAI, and run a test query.

6Gotchas worth knowing before go‑live

  • Single instance only. The rate limiter, in‑flight query‑cancellation registry, and schema‑introspection job status all live in process memory. With two replicas, a cancel or a status poll can land on the wrong instance and silently no‑op. The deployment doc says the same: one instance, or sticky sessions if you must scale.
  • Groups overage (200 memberships). Past 200 group memberships (the JWT limit; SAML tokens cap at 150) Entra drops the groups claim and substitutes a Graph pointer the app does not follow — affected users lose admin and group‑based assignments, with a [auth] Identity provider reported a groups overage log line — and if AUTH_ALLOWED_GROUPS lists only groups, they are locked out entirely (the sign‑in gate fails closed, logging [auth] Sign-in denied ... groups overage). Using App Roles avoids this class of failure entirely.
  • Role/group changes need a re‑login. Claims are read only when the JWT is minted; granting someone admin takes effect after they sign out and back in.
  • Missing email is fatal. The users table requires an email; the app falls back email → preferred_username → upn. Entra always issues a UPN in practice, but if you see [auth] Failed to upsert user in logs, this is why.
  • Sharing requires a prior login. The share picker only lists users who have signed in at least once — teammates must log in before you can share a connection or report with them.
  • Schema upload precedes queries. Each connection's schema must be introspected and uploaded to OpenAI (file + vector store) before natural‑language queries work. Vector stores can expire — re‑upload fixes 404s.
  • Redeploys are safe. Migrations are idempotent (tracked in schema_migrations), and all durable state is in PostgreSQL — the container itself is stateless in auth mode.
